| D02-V01 — C02, before §6. Capture in loops and asynchronous callbacks | Which returned methods share count, and which counter is independent? Misconception: A closure freezes its creation-time value or all factory calls share local state. | After the two increments above, A’s methods share the updated binding. A second makeCounter() call starts a separate count at 0. Arrows mean binding access, not physical memory placement or an exact retention graph. Closure capture keeps access to state; it does not snapshot the initial number or guarantee authorization. [Reference](https://developer.mozilla.org/en-US/docs/Web/JavaScript/Guide/Closures). |
| D02-V02 — C03, before §5. Arrow functions and lexical `this` | Why does the same read function work as a method and fail when detached? Detaching copies the function value without permanently binding meter. Strict mode is essential to the undefined receiver shown here. Arrows and bound functions have different receiver rules, explained below. [Reference](https://developer.mozilla.org/en-US/docs/Web/JavaScript/Reference/Operators/this). |
| D02-V03 — C04, before §4. Constructor functions and new | Why is account.role readable even though account does not own role? | D02-V04 — C05, before §3. map, filter, reduce, find and some/every | What changes when sorted has a different order but shares original’s objects? | D02-V05 — C06, before §4. Linking, instantiation and evaluation | Why does a live count read change while a primitive snapshot stays 0? Adding const snapshot = count before increment() would copy 0 into a separate local binding. The importer cannot reassign count. Read-only imports still allow mutation of writable properties on an exported object; ESM binding semantics do not freeze objects or specify CommonJS interoperability. [Reference](https://developer.mozilla.org/en-US/docs/Web/JavaScript/Guide/Modules). |
| D02-V06 — C07, before §3. catch bindings and unknown failure shapes | How does finally decide which return or throw leaves the function? Other abrupt exits, such as a valid break or continue, can also replace the pending outcome. A synchronous finally does not wait for a bare returned Promise. [Reference](https://developer.mozilla.org/en-US/docs/Web/JavaScript/Reference/Statements/try...catch). |
| D02-V07 — C08, before §2. Synchronous executors, asynchronous reactions | Can outer already follow inner while still being pending? Resolving here fixes what outer follows, so later attempts to resolve or reject outer cannot change that choice. These boxes describe this adoption case, not a fourth Promise state or a complete thenable-resolution algorithm. Settlement is eventual via Promise jobs, not necessarily immediate at finish(). [Reference](https://tc39.es/ecma262/#sec-promise-objects). |
| D02-V08 — C08, before §3. Chaining and recovery | Why does C appear before D even though p is already fulfilled? [Reference](https://tc39.es/ecma262/#sec-performpromisethen). |
| D02-V09 — C09, before §5. Deadline and timeout | What if cancellation happens after remote success but before confirmation arrives? [Reference](https://developer.mozilla.org/en-US/docs/Web/API/AbortSignal). |
